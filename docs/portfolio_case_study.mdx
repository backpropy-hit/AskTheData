## Problem

Nonprofit staff often keep their numbers in databases but cannot write SQL. Large language models can translate a question into SQL, but the query can be wrong, and in a careless setup it can even change the data. Most demos show a few good answers and never say how often the answers are correct.

I wanted to build a careful version. It should generate SQL from a plain-English question, check the query before running it, make sure it can never write to the database, and **measure** its accuracy on questions it has not seen.

## What I built

**Ask the Data** answers questions about refugees, asylum-seekers, internally displaced people and population. The data comes from UNHCR and the World Bank, linked by country code.

- **Data layer.**
  - A loader turns the public CSVs into a three-table SQLite database (`countries`, `population`, `displacement`) with keys, foreign keys and indexes.
  - The displacement table has two country columns (origin and asylum), so some questions need the country table joined twice.
- **Prompting.**
  - The prompt contains the real `CREATE TABLE` statements, a one-line description of every column, and the actual values of categorical columns, such as region names and unusual country spellings.
  - Two variants are compared: zero-shot (schema only) and few-shot (schema plus worked examples).
  - The model is told to reply with a fixed "cannot answer from this data" message when the tables cannot answer a question.
- **Safety in two layers.**
  - A sqlglot-based validator accepts exactly one `SELECT` over the known tables. It blocks writes, `PRAGMA`, `ATTACH`, table functions and multiple statements, and adds a row limit.
  - The query then runs on a read-only SQLite connection with a time limit, so even a validator bug cannot change the data.
- **Self-correction.** If the validator rejects a query or SQLite reports an error, the error message is sent back to the model once.
- **Evaluation.**
  - Hand-written questions with gold SQL, in easy, medium, hard and unanswerable groups.
  - Scored by execution accuracy: the generated query must return the same rows as the gold query.
  - Three strategies compared: zero-shot, few-shot, and few-shot with one retry.
  - Failures sorted by type.
  - A test fails if any few-shot example matches an evaluation question, so the accuracy number is not inflated by leakage.
- **App.**
  - A Streamlit interface shows the generated SQL, the result table, a simple chart when the result suits one, clear error messages and a per-session history.
  - It is deployed on Streamlit Community Cloud and builds its database on first start from the public APIs.
- **Engineering.** Modular package, typed config, a pytest suite that runs without network or data (fake model, small fake dataset), and GitHub Actions CI with ruff and pytest.

**Limitations I would mention in an interview:**

- The evaluation set is small and written by one person.
- Model behaviour changes between versions, which is why every result records the model and run date.
- Execution accuracy can pass a wrong query that happens to return the same rows, and can fail a correct one that returns columns in a different order.
- The validator reduces risk but is not a guarantee; the read-only connection is the second layer.
